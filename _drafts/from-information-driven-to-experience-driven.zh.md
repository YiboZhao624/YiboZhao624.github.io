**TL;DR：当信息获取变得越来越简单，我们似乎仍旧不知道，怎样把经验组织成对未来持续有效的信息。提炼经验时，我们还不知道未来会怎样使用它；应用经验时，我们又必须决定哪些可以固化，哪些仍需验证。如果进一步声称实现了自进化，评测就应该回答：系统只是更会完成任务了，还是连“如何继续改进自己”也学得更好了？**

之前很长一段时间，我都在做 RAG。我的出发点很直接：LLM 无法把所有内容都记在参数里，一个部署后参数基本固定的模型，也不会自动跟上外部世界的变化。新论文、内部文档和刚刚发生的事情，需要通过外部检索进入上下文。那时我关心的是，怎样找到模型需要知道的东西。

后来，我逐渐转向 search agent。一次检索不够，就继续搜索；问题需要多个步骤，就让模型根据已经找到的线索决定下一步。模型可以在 web 中导航、修改关键词、交叉验证和整理信息，搜索逐渐成为任务执行过程中的一种行动。

这个过程中，我越来越感到 search 正在成为 Agent 的基础原子能力。搜索或许还有难题，但是当[BrowseComp](https://arxiv.org/abs/2504.12516)这种专门构造难以查找答案的任务都快要饱和，“能够自己去搜”似乎已经成为默认要求。在某些资料搜集任务上，Agent 展现出的覆盖面和耐心，甚至让一个熟悉领域的人类研究者也很难跟上。

信息越来越容易获取之后，我的关注点也开始变化：一个 Agent 这次搜过、试过、失败过，下一次到底留下了什么？

与此同时，我看到越来越多熟悉的 RAG 问题被放进 Memory 的 narrative。我们仍然在讨论存储、组织、检索和更新，只是处理对象变成了“记忆”。如果只看实现，一段文本写进数据库，之后再检索出来，这和文档库确实可以很相似。但从内容的产生过程来看，区别很大。

论文、教程、说明书，通常已经经过人的组织。作者替读者做了一轮筛选，决定哪些事实重要、哪些背景需要解释、哪些结论需要保留条件。文档进入 retriever 之前，往往已经被加工成了可以交流的知识。

Agent 的原始经历里，则可能同时存在工具输出、重复尝试、错误猜测、临时文件和偶然成功。几万 token 的轨迹，未必能提供很多可复用的经验；一句看上去不起眼的报错，却可能是未来排查问题的关键。这里的信息量，我更关心的是它能为未来决策提供多少帮助。

原始经历也未必对 retriever 友好。两个任务的表述完全不同，失败原因却可能相同；两个任务看上去非常接近，也可能因为一个前提变化，就不能采用同样的办法。检索到一段相关经历，距离知道应该怎样借鉴它，还有一段路。

很自然，我们会让模型先把经历压缩一下：提取关键步骤，分析失败原因，写出 lessons learned，再在下次任务中使用。[Reflexion](https://arxiv.org/abs/2303.11366)通过语言反思与记忆让反馈影响之后的尝试，就体现了这种思路。

但我觉得，这里最难的部分是：**我们需要根据未来的用途提炼经验，但在提炼经验的时候，未来的用途还没有完全显现。**

假设一个 Agent 修改代码后测试失败，几次尝试之后，最终通过调整依赖版本解决了问题。我们可以把它总结成“遇到这种错误，检查依赖版本”。但原始轨迹里也许还有很多细节：错误只在某个运行环境出现，某个测试一直能够通过，另一个看似合理的修复反而破坏了兼容性。

如果未来只是重现这次修复，一条简短结论可能已经足够。如果未来需要判断为什么两个环境行为不同，那些被压缩掉的细节就变得重要。同一段经历，面对不同问题时，应该保留的内容并不一样。

因此，压缩得更短、对原始轨迹概括得更准确，都不能自动推出它对未来更有用。在写入时就提炼记忆，实际上隐含了对未来任务的预测：哪些信息值得保留，哪些信息大概率不会再用到。

这也是我们在 [LazyMem](https://arxiv.org/abs/2607.22690) 中讨论的动机：写入时压缩可能丢失未来查询需要的细节，因此把记忆构建推迟到 query time，先获得候选内容，再根据当前问题选择和压缩。至少到了这个时候，我们已经知道这一次要找什么。

但这并没有消除经验组织的全部困难。保留原始记录，需要在未来承担检索和推理的成本；提前提炼，则需要现在就承担选择和归因的风险。即使原始记录仍然可追溯，系统也可能长期只使用那几条摘要。真正值得研究的是，哪些判断可以推迟，哪些内容值得提前加工，以及什么情况下需要重新回到原始证据。

再往前走一步，即使我们已经提炼出一条经验，也还没有决定应该怎样使用它。

我后续很想研究的一个问题就是：**什么经验值得固化，什么经验应该保留为有条件的建议，什么经验需要继续验证？**

比如“修改代码后运行相关测试”。这条经验可以被写进 memory，等待未来被检索；可以进入通用指令，让模型在更多任务中考虑它；也可以直接写进 harness，让执行流程在修改之后自动触发检查。这里的 harness，指的是 Agent 的工具、上下文管理和执行流程等外围机制。

从这个角度看，memory 和 harness 可以是同一条经验影响行动的不同方式。前者通常还需要经过检索、理解和选择，后者可以直接参与执行。固化得越深，我们往往越容易保证它被执行，但也需要更认真地检查它的适用范围。

一条只在特定环境下成立的排错建议，偶尔被错误检索一次，与被写成所有任务都必须遵守的流程，代价并不一样。反过来，一条已经反复验证、适用范围清晰的经验，如果每次都需要重新检索和推理，也可能浪费资源，甚至在关键时刻被忘掉。

所以我关心的不只是“把经验存在哪里”，还有它应该处于什么状态。一次成功之后，它也许只能算一个候选解释；在多个不同场景中成立之后，才适合成为稳定建议；当触发条件能够明确检查时，才更有理由把它固化为执行规则。出现反例之后，它又应该能够被修订、缩小适用范围，甚至撤销。

这不是一套已经验证过的方法，而是我想研究的问题：系统能否根据证据，决定一条经验应该拥有多大的影响范围，以及多强的执行约束？

人类学数学也会碰到类似的事情。看完答案，把解法抄进错题本，可以帮助我们记住一道题。但如果希望换一道题仍然会做，就需要知道那个方法为什么成立、哪些条件不可缺少，以及什么时候应该换一种思路。

以利用奇偶性计算积分为例。一个学生可能记住“奇函数的积分是零”，也可能真正理解：在可积的前提下，奇函数在关于零对称的区间上，正负两侧的贡献能够抵消。两种理解在一些题目上会得到同样的答案，但在另一些题目上，区别很大。

如果函数满足 `f(c+t) = -f(c-t)`，积分区间是 `[c-a, c+a]`，他能不能认出这是平移之后的同一种结构？如果函数是奇函数，但积分区间变成了 `[0, 1]`，他会不会仍然直接写零？如果这道题根本没有可利用的对称性，他是否愿意及时放弃这个方向？

我们说一个人“消化、吸收”了经验，通常期待的就是这种有条件的迁移。死记硬背的问题也在这里：保留了解题动作，却没有很好地保留动作与条件之间的关系。一个很好用的技巧，很容易变成到处套用的 stereotype。

如果 Agent 的经验积累最后也产生了这样的思维定式，那么它可能在一类任务上更强，同时在另一类任务上更差。经验越多，并不自动意味着行为越合理。

可惜，信息流里的叙事往往前进得更快。把经历整理成文本，写进记忆，是 Memory；换一种结构，增加几种压缩模式，又可以形成一篇新 paper；再调用一个 coding 能力更强的模型，根据经验修改 harness，故事就变成了 self-evolving。

这些路径有真实的技术差异，也值得研究。[Darwin Gödel Machine](https://arxiv.org/abs/2505.22954)就在探索修改自身代码、通过编码任务评估改动，并维护候选 Agent 的过程。但从“系统发生了什么改动”到“系统获得了什么能力”，仍然需要实验来连接。

Memory、self-improving、self-evolving、RSI，各种 hype 和 buzzword 轮流登场。每天刷一遍，感觉已经经历了好几次原子弹爆炸，震惊、瘫坐，再震惊、再瘫坐。

等我站起来，还是想问：所以，它到底进化了什么？

**我最不满意的地方，是 claim 的范围，经常比评测实际覆盖的范围大得多。** 原题重试的提升被写成学会了经验，某个任务分布上的收益被延伸成普遍的持续学习，多个版本的分数上涨又被进一步放进 RSI 的故事里。这些推论之间，都缺少不能省略的证据。

一个方法只在明确限定的领域里有效，完全可以是扎实的贡献。如果 claim 就是提高某类任务的成功率，那么相应的独立测试和成本比较就很有价值。但如果要进一步声称获得了可迁移的经验，甚至持续自我进化的能力，评测也需要跟着这个范围向前走。

还是用积分的例子。我会希望看到这样一个小型实验：先让 Agent 从一批利用奇偶性求积分的任务中积累经验，然后冻结这批经验，在几组事先留出的任务上评测。

| 后续任务 | 它帮助我们区分什么 |
| --- | --- |
| 换一个函数，保留相同求解结构 | 收益是否超越对原题的记忆 |
| 把对称中心从零平移到其他位置 | 是否能够迁移到表面不同、结构相同的问题 |
| 保留函数对称性，但改变积分区间 | 是否掌握经验成立的条件 |
| 使用对称性没有帮助的积分题 | 是否因为新经验而产生方法偏执或额外开销 |
| 经验影响范围内的其他任务 | 是否出现能力退化或不恰当的策略迁移 |

实验中还可以比较几种处理方式：保留原始轨迹、生成摘要、把经验写入执行流程，以及不给予这批经验、但允许使用相当计算预算的系统。不同方式使用相同来源的经历，并明确报告构建和使用经验的成本。

这样的实验不直接告诉我们哪种方法最好，却能够区分几种很不同的解释：它是记住了更多答案，学到了适用范围更清楚的规则，更稳定地执行了已有知识，还是主要靠更多计算获得收益？如果收益只出现在第一组任务，论文仍然可以成立，但 claim 就应该停留在证据支持的位置。

平均分容易掩盖这些差异。正迁移可以抵消负迁移，更高的成功率也可能伴随更多无效尝试。如果我们只报告一个总分，就很难判断这条经验究竟改变了什么。对于广泛共享的 memory 或 harness，尤其需要检查其影响范围内的其他能力。

这也是为什么我认为，budget、测试边界和 metrics 是这个方向的核心，而不是论文最后补上的实验细节。

Budget 应该覆盖轨迹生成、反思、候选搜索、外部强模型调用、训练和失败的实验，同时区分前期投入与后续每次使用的成本。一条经验需要复用多少次才能收回构建成本，也是有意义的问题。如果基线只能直接回答，而新方法可以先花大量计算搜索一个更好的系统，我们至少应该把这笔投入摆在同一张账单上。

测试边界则决定我们到底在测优化，还是测泛化。只要某组题的反馈参与了记忆更新、代码修改或版本选择，它就已经进入优化循环。即使不提供标准答案，反复根据这组题的表现选择版本，也可能逐渐适应它。最终的泛化判断需要独立、未参与这些选择的任务。

而当 claim 上升到 recursive self-improvement，仅仅补上更多下游任务，还不够。我更想把问题明确地提到**二阶改进**上。

为了说明这里的意思，我把“更会完成任务”称为一阶改进，把“更会产生后续改进”称为二阶改进。这只是本文用来区分问题的说法，并不是一个已经统一的 RSI 定义。

一个固定的强模型不断给 Agent 提出修改，再通过评测筛选出更好的版本，完全可能让任务分数持续上涨。这证明了这套优化流程能够找到改进。但分数上涨本身，还不能说明后来的系统比先前更善于继续改进自己。

人类的类比是：学会一个积分技巧，和学会怎样安排练习、诊断自己的错误、选择更有帮助的反馈，不是同一层面的进步。后者可能让我们之后学习新技巧时，更有效地利用时间。

对应到 Agent，我希望追问的是：**在相同的后续预算下，进化后的系统，是否比进化前的系统更善于发现、评估和实现新的改进？**

它是否更会选择有区分力的实验，更少重复已经失败的方向，更准确地淘汰无效改动？它是否能够用更少成本获得同样幅度的提升，或者在同样成本下实现更大、可泛化的提升？这些都比“新版本的最终分数更高”更接近二阶改进的含义。

一个可以考虑的诊断实验，是把进化前后的系统分别作为“改进者”，让它们面对同一组起始 Agent 和新的开发任务，获得相同的工具、反馈权限和预算。比较它们产出的修改在独立测试任务上的收益，并记录到达目标收益所需的成本。这样至少能减少起始版本本来就更强、或者提升空间不同带来的混淆。

还需要一个固定改进者的对照：保持提出修改的系统不变，只让被修改的 Agent 持续更新。如果这种方式已经能解释大部分收益，那么递归关系的额外价值还需要继续证明。反过来，如果更新后的改进者在新的改进任务上也稳定更有效，才提供了更直接的二阶证据。

这个实验也不能单独证明开放式、长期的 RSI。为了支持那个更强的 claim，我们还需要看到改进能力的提升确实来自自身改进循环，并能在更多轮次和新问题上继续发挥作用。但至少，我们开始测量叙事里最关键的那个“recursive”，而不只是把一个上升的任务分数重新命名。

我对当前很多强叙事的悲观，主要来自这里。我们已经有很多让系统发生变化的办法，也有很多证明某种变化有局部收益的实验。但从局部收益走到可迁移的经验，再走到二阶改进，每一步都需要不同的证据。

受限于资源，我可能没法在别人给出答案之前，完成自己想做的全部实验。不过我还是想在这里写下自己的 vision。

在预算和测试边界清楚的前提下，我希望给 Agent 更多自由。如果每一轮都由人规定它应该总结什么、按什么模板反思、修改哪段代码、运行哪个实验，那么我们观察到的学习方式也被限制在这套流程里。

我更想把一个问题和一笔有限的 GPU hours 交给它，让它决定接下来做什么：整理数据，设计一个小规模对照实验，修改训练方案，验证一个失败假设，或者终止一个不值得继续的方向。Just like human researchers。

这也把前面的几个问题连在了一起。它需要从过去的实验里提取有用的东西，知道哪些结论已经足够可靠、哪些只是猜测，再据此分配下一笔预算。而一次新的实验，也可能改变它之后选择实验的方式。

短期内，我其实有一些很具体的期待。先让 LLM 做好自己的 data preparation，检查数据质量和混合比例；让它持续监控训练曲线，根据证据决定什么时候调参、继续等待，或者停止一次训练。这些事情做好，本身就能为研究者节省很多时间。

但在我目前的使用体验里，模型经常更擅长解释已经发生的事情。你给它一条曲线，它可以列出很多原因；你提出一个判断，它可以补充支持理由和限制条件。等到必须消耗下一笔真实预算时，我仍然经常需要替它做最后的选择。

比如训练 loss 在下降，验证表现却没有改善。它可以列出过拟合、数据分布不匹配、评测噪声等解释。可接下来应该检查数据、按子集重做评测，还是继续训练？这些行动的成本不同，能排除的假设也不同。一个有研究能力的系统，需要把可能的解释转化成有优先级的实验。

所以我期待的那句“听我的”，关心的是决策能力。信息不完整时，它仍然应该能够提出一个可检验的选择：先做什么，最多花多少资源，什么结果会让它改变判断。过去的经验应该让这些选择越来越有效。

我希望它能够说：“听我的，先跑这个小实验。它最能区分我们现在的两个假设；如果结果不支持，我就放弃这个方向。”然后把实验做好，并真的根据结果更新自己。

这也是我想从 information driven 走向 experience driven 的原因。搜索让 Agent 更容易得到外部世界已经组织好的信息；从经历中学习，则要求它自己承担选择、归因、验证和修正的工作。当这些工作也能随着经验积累而改善，我们才更接近一个持续成长的系统。

也许有一天，真的会有人造出 RSI 的 LLM。它可以在持续、独立的检验中证明，自己不仅在变强，也在变得更善于继续改进自己。那时候，RSI 终于有了与名字相称的证据。

然后我们全都失业了。

既然总有人要革我的命，那为什么不是我自己呢？
